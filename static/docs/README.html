About Planning Poker game

Planning Poker is a consensus-based estimation technique used in Scrum to size user stories or backlog items. Each participant is given a set of cards showing a sequence of numbers (often the Fibonacci sequence: 1, 2, 3, 5, 8, 13, etc.).

  1. For each item under discussion, the product owner briefly describes the story ①
  2. … and team members ask clarifying questions ②.
  3. When everyone feels ready, each estimator privately selects the card that best represents their effort or complexity estimate ③.

  4. All cards are then revealed simultaneously, preventing early anchoring on a particular number ④.

    This is the main idea behind this software so it can organize the process around voting. Of course, we can have used Slack to send private messages (PM) to our Project Manager (PM->PM) so s(he) can collect and reveal it, but using tool is better.

Here’s a Sequence Diagram in PlantUML showing your Scrum Planning Game flow: 

@startuml
actor Facilitator
actor "Business Analyst" as BA
participant Developers
participant System
participant Jira

Facilitator -> Developers : Brief on task ①
BA           -> Developers : Brief on task

loop Q&A
  Developers -> Facilitator : Ask question ②
  Facilitator -> Developers : Answer
  Developers -> BA          : Ask question
  BA          -> Developers : Answer
end

Facilitator -> System : Start voting

loop Voting
  Developers -> System : Submit vote ③
  System     -> Developers : Update count (votes cast)
end

Facilitator -> System : End voting
System -> Developers : Reveal all votes ④

System -> Jira : Post/update estimate comment

@enduml

If estimates vary widely, the high and low estimators explain their reasoning, and the group discusses assumptions and hidden complexities. After this discussion, the team votes again, repeating the process until a consensus emerges. This method encourages active participation, surface-level ambiguity reduction, and shared understanding of requirements.

Planning Poker is important because it leverages collective wisdom, balances influence among senior and junior team members, and reduces cognitive biases like anchoring. By forcing discussion of differing viewpoints, it uncovers hidden risks and dependencies early. Ultimately, it leads to more accurate, realistic estimates, stronger team alignment, and a higher likelihood of delivering value within the sprint.

Install

Backend: 

uv install

Frontend: 

cd pp-front
yarn install

Setup

Copy & edit contents of .env file: setup variables 

cp .env-example .env

To do this you will need to create Google Project and obtain Oauth authorization keys.

I also found it quite unconvinient when all comments are made from my account (because I was originally using my personal Jira token to post/modify the comment). To avoid being spammed by all team member emails later I had to develop Jira Oauth2 access as well. To set it up, you need to run authroization once, and when your login process is performed, please copy your JIRA_CLOUD_ID into .env, this is printed here.
